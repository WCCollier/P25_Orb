# P25 Orb — As-Built Summary

Everything that was produced, what is real and what is not, where each piece
lives, and the order to read it in.

This is the document to start from if you are picking this up cold — including
if the person picking it up cold is you, a week from now, an hour before the
presentation.

---

## Running it

```
python3 serve.py
```

Then open **http://localhost:8000** and follow the links.

That is the whole setup. No build step, no bundler, no `npm install`, no
`pip install`. The demo is plain HTML, CSS and JavaScript, and `serve.py` is
Python's own standard-library web server with one extra endpoint.

**Why there is a server at all**, given "no build step": the *Try it live* page
makes a real Anthropic API call, and an API key must never be shipped to a
browser. Anything in client-side JavaScript is readable by anyone who opens
developer tools, or by anyone who later reads the repository. So the key stays
server-side and the browser posts a phrase to `/api/classify` without ever seeing
the credential.

**The scripted two-tab demo does not use that endpoint and needs no network and
no API key.** If `.env` is missing, the presentation still runs; only the *Try it
live* page stops working, and it tells you so on load.

### Verifying it still works

```
node test/engine-test.js      # 47 assertions on the detection engine
node test/ui-smoke-test.js    # 16 assertions on the two-tab wiring
python3 df/test_aoa_fix.py    # 20 assertions on the direction-finding solver
```

All three pass with no dependencies. Run them after any edit.

### Regenerating the AI classifications

```
python3 tools/generate_classifications.py
```

This calls the model once per transmission and rewrites
`demo/js/classifications.js` and `tools/classification-log.json`. You should not
normally need to — the cached results are committed. Only run it if you change
the timeline or the prompt, and **run the engine test afterwards**, because
different labels can change what the engine decides.

## What is real, and what is not

The single most important thing to be able to answer under questioning.

| Piece | Status |
|---|---|
| Detection, synthesis and alarm engine | **Real working code.** Every alarm in the demo is computed from the event stream. 47 automated assertions. |
| AI classification | **Real model output.** Genuinely generated by calling Claude Haiku 4.5, cached for the presentation, raw API responses kept as evidence. |
| Live classifier demonstration | **Real API call**, made at demo time, using the same prompt and model. |
| Command Feed | **Real**, driven live over `BroadcastChannel` by the RF Environment tab. |
| RF Environment / diagnostics view | **Real** player and renderer. |
| Direction-finding solver | **Real working code**, 20 assertions. Standalone — not wired into the demo. |
| Control Panel | **Static mockup.** Renders; does nothing. |
| The radio events themselves | **Simulated.** A scripted timeline — not because of any ARC Edge access limitation, but because no P25 receiver hardware exists for this demo. Terminology and data shapes are accurate. |
| ARC Edge path selection (DMPO) | **Represented narratively**, not implemented. It is Orb Aerospace's intellectual property. |
| Live audio pass-through | Not built. A real capability of the design; out of scope for this demo. |
| Anything requiring a transmit licence | Not built. Roadmap. |
| Existing-Radio Interface tier | Not built. Roadmap. |
| P25 Hotspot (fourth product) | Not built. Roadmap — `design-document.md` §5.1. |

### How the demo marks what it has not built

Several capabilities are specified in the design documents but do not exist in
code — receiver sensitivity reporting (`software-prd.md` §1.5), multi-unit
cooperation (§6), the map layer. Rather than leave them off the screen and
describe them from the stage, **they appear on the relevant page as dashed
panels chipped "not built", each naming the requirement it stands for.**

Two reasons, and the second is the one worth giving if asked:

- A viewer never has to work out which parts of the demo are real. Anything not
  marked that way is working code.
- **It is the product's own principle applied to the product's own
  demonstration.** This system exists to stop an absence being mistaken for
  calm. A demo that quietly omitted its gaps would be committing the error it
  was built to prevent.

Nothing marked this way animates, updates, or is fed by the engine. Static by
design — a plausible-looking number next to real engine output is exactly the
confusion the convention exists to avoid.

## Suggested reading order

If you want to understand the system rather than just run it, read in this
order. Each step assumes the previous one.

**1. `design-document.md`** *(pre-existing)* — the authoritative specification.
Everything else implements or explains this.

**2. `demo/js/timeline.js`** — the scripted radio events. Start here rather than
with the code, because it is the input to everything else and it is readable
straight through. The comment at the top explains exactly which parts are
simulated and why.

**3. `demo/js/detection-engine.js`** — **the product.** If you only read one
source file, read this one. Pure state machine, no DOM, no network, no timers of
its own. The comments explain the corroboration rule and, more importantly, why
blocked transmission attempts are deliberately excluded from it.

**4. `test/engine-test.js`** — the engine's behaviour stated as checkable claims,
organised by the seven demo beats. This is the fastest way to understand what the
engine guarantees, and it is your evidence that the alarms are computed rather
than scripted.

**5. `docs/software-prd.md`** — requirements *and* the reasoning behind them. Why
two tiers. Why independence is enforced on two axes. Why the demo caches
classifications but still makes a live call. Why the production architecture is
hybrid cloud/local.

**6. `classifier.py`** — the AI layer. One prompt definition, shared by the
build-time job and the live endpoint, which is what makes "same pipeline" an
honest claim rather than a marketing one.

**7. `demo/js/command-feed.js`** and `demo/js/rf-environment.js` — the two views.
Read the RF one first; it is simpler and it owns the clock.

**8. `docs/hardware-design.md`** — the module. Block diagram, component
rationale, illustrative bill of materials, power budget, and what is still open.

**9. `df/README.md`** — direction finding, the standalone artifact.

**10. `pitch-script.md`** — the spoken pitch, with a Q&A appendix at the end.
**It runs about 25 minutes, not the 14 an earlier header claimed.** A timing
table at the top gives the per-section breakdown and a marked path down to ~17,
and notes that section 4's eight minutes of narration over a three-minute demo
means you will be pausing.

## The decisions most likely to be questioned

Short version of each, with a pointer to the full reasoning.

**Why a cut-off transmission raises only a Suspected alarm.** The fragment
`"Shots f—"` is both a truncation and a distress keyword. The engine records
**both** observations — the commander sees everything noticed — but the tier
stays Suspected, because both carry the same source event id and two readings of
one moment of audio are not corroboration. Independence is enforced on two axes:
different signal kinds *and* different source events. To confirm the rule is real
rather than decorative, delete `sources.size >= 2` from `tierFor` and five
assertions fail. Full reasoning: `docs/software-prd.md` §1.3.

**Why blocked transmission attempts never escalate an alarm.** When the trunk is
saturated everybody is blocked, so it is a fact about the trunk, not about the
person. They are counted, they drive the congestion picture, and they appear as
context on an existing alarm — but they never raise one. `software-prd.md` §1.3.

**Why nothing closes an alarm automatically.** A third party reporting that an
officer is fine is not the same as that officer answering, and even the officer
answering is not the same as a commander deciding it is over.
`software-prd.md` §1.3.

**Why the demo caches classifications instead of calling live.** No network
dependency in the critical path of a pitch about communications failing under
load. The claim stays checkable because the *Try it live* page uses the same
prompt, model and schema — enforced by both callers importing `classifier.py`.
`software-prd.md` §2.5.

**Why the engine does not simply trust the classifier.** It was observed getting
one label wrong — marking a routine transmission as a status check — and the
design absorbed it without incident, because a status check only starts a clock
when the subject resolves to a unit actually heard on the trunk.
`software-prd.md` §2.3.

**Why Haiku rather than a larger model.** It has to run on every transmission at
a busy scene, continuously. A model too expensive for routine traffic only runs
on traffic somebody already flagged, which defeats the point.
`software-prd.md` §2.4.

**Why receive-only ships first.** No licence, no cooperation from the trunk
operator, no unit ID, and a genuinely lower power draw because the power
amplifier is unpowered. It is the lean configuration, not a stripped-down one.
`docs/hardware-design.md` §6.

## Known gaps and things left honest

- **Enclosure and mechanical integration** with the ARC Edge Field Kit needs Orb
  Aerospace's own specifications. Not invented. `hardware-design.md` §7.
- **The interface protocol above Ethernet**, and precise power budget figures,
  need their engineering input. Same section.
- **A caveat found during hardware research and flagged rather than buried:**
  secondary sources on the Texas plan state that low-power direct channels like
  8TAC95D may not be used in a repeater configuration or patched through a
  gateway. If that holds as written, the roadmap's cross-band bridging cannot use
  8TAC95D as one leg. It does not affect the receive-only product being
  demonstrated. It should be confirmed against the plan text before any bridging
  feature is committed to. `hardware-design.md` §3.4.
- **Frequencies in the demo are illustrative**, except 8TAC95D at 851.5500 MHz,
  which is the real designated channel. LCRA's actual channel assignments were
  not used.
- **The AI classifier occasionally over-labels.** One case is visible in the
  committed output and is described above. This is not hidden; it is the reason
  the engine cross-checks.
- **The direction-finding artifact assumes the bearings exist.** The signal
  processing that extracts an angle from phase differences across an antenna
  array, and the calibration that makes it trustworthy, is real work that this
  artifact takes as input rather than solving. `df/README.md`.
- **Bearing accuracy has no measured figure, and the errors we can calibrate are
  not the dominant ones.** Array manifold and deployment geometry contribute
  perhaps 1–2° each and are ours to remove; multipath and site-induced
  magnetometer bias are supplied by the environment and survive bench
  calibration entirely. The budget, and why a two-station fix cannot detect a
  multipath error while a three-station fix cannot identify which bearing caused
  it, is in `hardware-design.md` §5.7. No performance figure should be quoted
  until measured.
- **The hardware is specified as two assemblies, and none of it is built.** A
  band-agnostic processing body docking into a band-specific module (housing,
  array, filters, PA/duplexer), with the dock plane after the filters and before
  the LNAs. Licensing is a software unlock, never a hardware upgrade — this
  restores what `design-document.md` §5 always said, after `hardware-design.md`
  had drifted into describing the PA as populated only on transmit builds.
  `hardware-design.md` §1.1, §3.1a, §3.4.
- **The engine consumes far less than the revised hardware could supply, and that
  is a deliberate choice.** Signal strength, SNR, per-radio frequency offset and
  undecodable-transmission detection are all available with no further hardware
  decisions; bearing and unanswered-request detection are gated on open hardware
  items. None is implemented. The audit — including why these matter more than a
  feature list, since they are *physical* signals that relieve the corroboration
  rule's dependence on the classifier — is `software-prd.md` §1.1a. What would
  have to change to adopt them is §1.1b, and why the AI classifier must **not**
  change is §1.1c.
- **Decoding P25 voice needs a licensed vocoder, and this is not resolved.** IMBE
  and AMBE+2 are Digital Voice Systems Inc. proprietary codecs. The open-source
  implementations hobbyist projects use are not a defensible basis for a
  commercial product sold to government. Terms and cost are uninvestigated, and
  it is a single-source dependency. **It does not affect the demonstrated
  product**, which reasons on control-channel signalling only.
  `hardware-design.md` §3.5.3, open item I.
- **Transcription quality is capped by the vocoder rather than the transcriber.**
  A better recogniser cannot recover detail the codec discarded. Do not quote
  clean-speech accuracy figures. `software-prd.md` §2.2a.
- **The demo does not model processing latency.** In reality, control-channel
  events reach the screen in under a second while speech-derived signals take
  roughly 2–5 seconds, so a SUSPECTED alert can be promoted to HIGH_CONFIDENCE
  seconds after it first appears. The demo's classifications are pre-cached and
  its timeline scripted, so everything appears instantly. `software-prd.md` §1.4.
- **Unit identity is keyed by a bare ID string, which is a real defect.** A P25
  unit ID is unique only within its own system, and an interoperability channel
  is cross-agency by definition — so even a single Orb can see colliding IDs.
  The fix is to key by `(WACN, SystemID, unitId)`; the Control Panel already
  collects the first two. `software-prd.md` §1.1.
- **The demo attributes unit IDs to analog talkaround traffic.** Real analog
  gives audio and no identity unless the fleet sends an ANI burst. Noted in
  `demo/js/timeline.js` and `software-prd.md` §1.1.
- **A further product is proposed and not built: the P25 Hotspot.** A dedicated
  P25 RF subsystem, vehicle or trailer mounted on generator power, creating local
  trunked coverage where the trunk is down, swamped or absent, ISSI-peered to the
  parent system or to other Hotspots over ARC Edge. `design-document.md` §5.1.
  **It is a separate product, not a tier** — it inverts the Orb's zero-cooperation
  virtue, requiring a licence, frequency coordination and a peering agreement.
  Two things worth carrying: the correct architecture is an **ISSI-peered
  subsystem, not a trunk site** (the site-to-core link is vendor-proprietary;
  ISSI is an open TIA standard), and **a Hotspot is a superset of an Orb** rather
  than a sibling.
- **Multi-Orb collective operation is designed and not built.** `software-prd.md`
  §6: replicated observation log plus the existing pure reducer, no master, with
  deterministic correlation as the load-bearing piece. Nothing multi-unit exists
  in code — `BroadcastChannel` is same-origin and same-machine, not a network.
- **Multi-unit association is proposed, not built.** `df/aoa_fix.py` takes
  already-associated observations as input. The four-tier strategy for deciding
  that two units heard the same transmission — decoded identity, GNSS timestamp
  plus channel, frequency-offset fingerprinting, geometric validation — is
  written up in `df/README.md` and none of it is implemented.
- **Transceiver selected: Analog Devices ADRV9026** — four coherent receivers on
  one die, on-chip multichip sync, 200 MHz bandwidth, JESD204B/C. Reverses an
  earlier AD9361 selection, which survives as the documented fallback (two
  synchronised devices). Decided on a **failure mode** rather than a costing: a
  multi-chip sync that half-succeeds produces a wrong bearing, not a missing one.
  `hardware-design.md` §3.3, §5.5.
- **Magnetometer arrangement selected**, no longer pending: two dedicated
  magnetometers at the outboard lid corners, IMU colocated with the inboard
  element at the centre hinge, on the storm-case band modules. **The VHF module
  is explicitly out of scope and undesigned.** `hardware-design.md` §5.8.
- **Enclosure resolved by design intent:** the processing body is a
  factory-assembled bolt-on to the ARC Edge unit, the pair lives in the storm
  case trunk, and the assembly slots into a band module. Requires Orb Aerospace's
  agreement and mechanical specs, and the storm case is our proposal — their
  confirmed Field Kit is a soft backpack.
- **The dynamic-range budget is the open question that matters most.**
  `hardware-design.md` §7.4. It is three mechanisms rather than one, the selected
  ADRV9026's published figures (81 dBc SFDR, IIP2 58–65 dBm, IIP3 15–18 dBm) are
  base-station-grade, ADC bit depth is unpublished, and **nothing has been
  measured.**
- **The transceiver change narrowed the tuning range, and that broke a claim
  about the product line.** [Found 2026-07-31.] The ADRV9026 tunes **650 MHz–
  6 GHz**; the AD9361 it replaced tuned 70 MHz–6 GHz. **VHF and UHF — two of the
  three band modules — are below the floor**, so "one processing body covers
  every band" stopped being true when the part changed and was not caught for a
  day. Proposed fix is block up-conversion inside those two modules, which keeps
  the body band-agnostic and arguably sharpens the module's interface contract;
  it is proposed rather than decided because the mixer's spurious products land
  on the dynamic-range budget above. `hardware-design.md` §3.3 and §7.4 item J.
  **The demonstrated 800 MHz system is unaffected.**

  *Worth knowing as a process point, not just a fact:* the transceiver decision
  was right on its own terms and still broke something two documents away. The
  habit of recording corrections as corrections is what surfaced it.
- **Instrument-health reporting is specified and not built.** The unit must
  detect and announce when a nearby transmitter has desensitised it, because no
  component choice removes that possibility. Six requirements in
  `software-prd.md` §1.5, including that a deafened receiver can *manufacture* a
  false `STATUS_CHECK_UNANSWERED` — which makes this a correctness requirement
  rather than a diagnostic. The proof of concept has no receiver and therefore no
  sensitivity to report.
- **The product line is specified as seven part numbers** — one processing body,
  three band modules, three clip-in duplexer packs. Every module is three-element
  and DF-capable, and every module transmits on interoperability channels; only
  the duplexer needed for licensed trunk participation is optional. None of it is
  built. `hardware-design.md` §1.1.1.
- **Direction finding is band-limited; the base product is not.** The array's
  size scales with wavelength, so 700/800 fits a case lid, UHF needs a larger
  case, and VHF needs a mast or vehicle mount. Receive-only monitoring works on
  every band with an ordinary whip. `hardware-design.md` §5.1.
- **The captured slice covers downlinks only.** The module as specified hears
  what the tower transmits, not what subscriber radios transmit — those are 45
  MHz away in the 800 MHz band. Everything the demonstrated product reasons about
  is either repeated onto a downlink or is simplex direct traffic, so this is
  correct for what was built. It does mean the module cannot hear a transmission
  the infrastructure never repeated. `hardware-design.md` §3.3.1 limitation 3,
  and §3.3.2 for what closing it would cost.
- **"Hearing what the network missed" (`hardware-design.md` §3.3.2) is analysis,
  not code.** The detection engine consumes an event stream and knows nothing
  about signal strength. It is documented because it is the strongest capability
  argument the architecture has, and it is labelled as unbuilt in every place it
  appears including the pitch script.
- **No dynamic-range budget exists.** Wideband capture cannot filter a strong
  in-band signal before the converter, so the strongest signal in the slice sets
  the noise floor for every channel extracted from it — in direct tension with
  weak-signal detection. `hardware-design.md` §3.3.1.
- **The block diagram gained an FPGA bridge after review.** The AD9361's LVDS
  I/Q interface cannot connect to a Jetson directly. The stage was missing from
  the first revision and is now item B3 in the body BOM. What runs on the FPGA versus
  the Jetson is not specified. `hardware-design.md` §3.5.1.
- **Magnetic heading integrity is an open design thread, marked PENDING.**
  `hardware-design.md` §5.8 proposes four approaches — two software-only, one
  adding a second magnetometer for gradiometry, one replacing the magnetometer
  with dual-antenna GNSS. **None has been selected, costed, or tested.** It is
  documented as a proposal, not a decision, and the hardware half of it should
  be settled before carrier-board layout.
- **The `.env` file holding the API key is gitignored.** If that key was ever
  pasted into a chat or shared anywhere, rotate it.

## If you change something

- **Changing the timeline** (`demo/js/timeline.js`) means re-running
  `tools/generate_classifications.py` if you added or edited a transmission, then
  re-running `test/engine-test.js`. New model labels can change engine behaviour.
- **Changing the engine** means re-running `test/engine-test.js`. The beat
  assertions there encode the demo script from the design document; if one fails,
  either the change is wrong or the demo narrative has moved.
- **Changing either tab's markup** means re-running `test/ui-smoke-test.js`. It
  checks every `getElementById` target against the ids that genuinely exist in
  the HTML, which is how a renamed id gets caught before a presentation rather
  than during one.
